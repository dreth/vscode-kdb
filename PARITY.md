# Standalone parity and architecture

This document is an evidence ledger, not a parity declaration. `vscode-kdb` is a standalone first-party implementation, but the `0.2.8` code has **not** completed functional or visual parity verification with KDB-X, q Professional, or other broad q development environments.

The comparison baseline is:

- `vscode-kdb` `0.2.8` plus the current Unreleased work, including client-side q script-line grouping with ordinary legacy-compatible `value` evaluation, Python-first mixed-notebook Make/Run actions with an explicit current saved-profile target, an optional q-only `KX q (Direct IPC)` controller disabled by default, delayed-propagation-safe multi-profile/active persistence, a shared KX Results panel/notebook UI contract, seven-format inline copy/export, visible-column controls, six capability-valid inline chart families with live refinement/PNG export, explicit live-versus-saved state, independent 30-minute query defaults, 20-row-default persisted previews with transient full live results, the separately released `kx-notebook==0.1.0` Python/IPython `%%q` route, the one-shot legacy KDB connection migration bridge, the focused first-party Server Explorer and Query History, and earlier standalone foundations.
- The comparison baseline remains `kdb-sqltools` `0.3.17` at `af2c7c9`. References outside the chart-interaction row name source and test symbols at that commit. The 0.2.5 work then landed the deliberately bounded hidden-series/legend/double-click compatibility backport as `kdb-sqltools` commit `ac41ccd6ab4baf4fde5a57d154920e108a6b2bf9`, followed by named refresh-path regression coverage in `879e2da649e5570f5f5645dac77e03574147af94`; only `src/chart-series-state.ts`, `src/results-panel.ts`, and `test/run.js` were committed across those changes. Pre-existing uncommitted generated-site changes in that checkout were neither staged nor used as evidence.
- The connection reliability comparison also examined `kdb-sqltools` commit `f2aab16` (`fix: harden kdb connection reliability`).
- q Professional's public `jshinonome/vscode-k-pro` snapshot at `fc9afacaeaf5e90eb013eb34426488841cc24f2a`. Its formatter documentation informed product-level readability research only. The repository license is all-rights-reserved; no code, logic, or assets were copied.
- Apache-2.0 `KxSystems/kx-vscode` at `1c745bf0221dd3cca85dce925c4d432d80bb5ef5`. Its source exposes qlint integration as linting rather than a general qText pretty-printer. No code, logic, or assets were adapted for 0.2.5.

The executable cross-extension gate is documented in [`test/parity/README.md`](test/parity/README.md). Its checked [`PARITY_RUN.md`](PARITY_RUN.md) / [`PARITY_RUN.json`](PARITY_RUN.json) snapshot ran standalone commit `0c1ca7ddfb4eb48f788f8b32cf865340da2410dd` against the pinned reference and real q. It classified all 63 cases across 381 assertions: 49 `PASS`, 5 `DIFFERENT_BY_DESIGN`, 3 `GAP`, and 6 `NOT_TESTABLE_HERE`; the result is `VALID_WITH_KNOWN_GAPS`, not source-of-truth sign-off. Those executable classifications are bounded case outcomes. The broader Present/Partial/Missing labels below describe current product state and must not be inferred from one passing core case.

Status meanings:

- **Present**: the standalone path exists and has direct automated evidence appropriate to this pass.
- **Partial**: useful implementation exists, but behavior, coverage, UX, or a reference capability is still incomplete.
- **Missing**: the standalone path does not exist. Rows marked intentional must not be recreated merely to mimic SQLTools.

## Competitive capability audit

Server Explorer, Query History, Python-first mixed direct-q notebook execution, the optional q-only controller, and portable notebook snapshots close practical standalone workflow gaps, but their presence is not evidence of full KDB-X or q Professional parity. The explorer intentionally covers one active direct connection and one configured namespace, with read-only metadata and confirmed previews. Mixed q cells resolve their explicit saved-profile target on every run; the q-only controller uses the active profile only when explicitly enabled and selected. Public APIs still select one notebook controller; normal Python Run is never rerouted, and the native Jupyter selector remains. The product does not reproduce multi-environment administration, Insights/gateway workflows, server management, broad namespace navigation, write operations, every persistent widget interaction, or every editor convenience.

- [q Professional / `jshinonome/vscode-k-pro` at `fc9afacaeaf5e90eb013eb34426488841cc24f2a`](https://github.com/jshinonome/vscode-k-pro/tree/fc9afacaeaf5e90eb013eb34426488841cc24f2a) documents a formatter and was reviewed for product inspiration only. Its public repository is all-rights-reserved; no code, logic, or assets were copied.
- [KX's `KxSystems/kx-vscode` at `1c745bf0221dd3cca85dce925c4d432d80bb5ef5`](https://github.com/KxSystems/kx-vscode/tree/1c745bf0221dd3cca85dce925c4d432d80bb5ef5) was inspected under Apache-2.0. Its `kdb.ls.q.lint` command is qlint integration—linting, not a general qText result pretty-printer. No code, logic, or assets were adapted for 0.2.5, so no new Apache-derived file or third-party notice is claimed.
- SQLTools and `kdb-sqltools` remain absent as runtime/UI dependencies. The standalone views, storage, execution integration, migration review, and tests are KX-owned implementations rather than SQLTools adapters. Reading an existing VS Code setting on explicit command invocation does not transfer SQLTools runtime/session ownership.

## Architecture boundary

No product/runtime monorepo, cross-repository dependency, symlink, generated copy, private Jupyter integration, or SQLTools package was introduced. The migration bridge retained in 0.2.5 contains only independently implemented schema knowledge and a read-only VS Code configuration ingress; no reference code or asset enters the standalone runtime or artifact. The compatible SQLTools hidden-series fix is a deliberate separate-repository backport, not a standalone runtime dependency.

Later extraction should start **inside `vscode-kdb`**, preserving it as the future source-of-truth candidate:

| Future boundary | Safe core | Keep in the standalone adapter / compatibility adapter |
| --- | --- | --- |
| q wire and values | q IPC codecs, receive buffering, q value types, q error type | TCP socket lifecycle, OutputChannel wiring, SQLTools driver conversion |
| q execution | namespace wrappers and script grouping helpers | editor selection policy, commands, connection picker, SQLTools current-block aliases |
| results | columnar storage, cell formatting, sorting, text/XLSX serialization limits | VS Code webview lifecycle, clipboard/save dialogs, command IDs, setting namespaces |
| notebooks | versioned bounded MIME schema, typed portable cells, escaping/static fallbacks, chart specification, pure selected-cell/language/default/marker models | VS Code supported document-language setter, NotebookRenderer/messaging, IPython evaluator registration, cell commands/metadata, controller/live session ownership |
| charting | inference, sampling, grouping, OHLC validation/aggregation, box statistics | webview controls, uPlot lifecycle, theme and persisted panel state |
| local data | token/range/format validation and response serialization | listener ownership, active-panel routing, notifications |
| diagnostics | allowlisted fields, secret redaction, duration formatting | `KX` OutputChannel and extension-specific lifecycle events |

The first extraction step is a file-boundary refactor with unchanged behavior and parity tests in this repository. Only after those interfaces stabilize should a compatible subset be deliberately backported to `kdb-sqltools`. A live dependency from standalone to SQLTools, or a shared SQLTools UI/session abstraction, is explicitly out of bounds.

### M3 — bounded notebook renderer/protocol (0.2.0)

That release shipped a real NotebookRenderer, versioned bounded MIME serializer, durable `%%q`/namespaced metadata convention, static export fallbacks, and focused explicit-evaluator IPython helper. It did not contribute a placeholder controller or reinterpret `.q` files as notebooks. Renderer reopening worked from saved output without the originating live session; only the saved preview was available.

At that milestone, extension-driven same-session cell execution, live-result ownership, and controller-owned cancellation were deliberately deferred and disabled. The 0.2.3 direct controller closes that architecture gap through supported VS Code notebook APIs and the existing first-party connection lifecycle; private Jupyter interception and hidden second connections remain prohibited.

### M3.1 — actual notebook q language UX (0.2.2)

That release used VS Code's supported document-language setter to make selected Jupyter code-cell documents genuinely q, added discoverable toolbar/context/Command Palette actions, restored a safely resolved notebook default, and kept one durable `%%q` preparation path for the current Python-kernel evaluator. VS Code's built-in serializer records a non-default q cell under raw `metadata.vscode.languageId`; at that milestone the generic picker was controller-filtered and no q-capable controller existed.

This did not make the normal Python controller execute q-language cells. The Python `%%q` helper remains supported as a separate same-Python-kernel route in 0.2.3 and still does not share state with Direct IPC by implication.

### M3.2 — native KX q Direct IPC controller (0.2.3)

The release registers `vscode-kdb.q-notebook-controller` through `vscode.notebooks.createNotebookController` for `jupyter-notebook`, advertises q, activates on Jupyter notebooks, and appears in VS Code's normal kernel/controller selector as **KX q (Direct IPC)**. Normal notebook Run executes the complete q cell through the existing active KX connection, client, and namespace. It does not intercept the Python controller, call private Jupyter APIs, or create a per-cell/per-notebook connection.

Direct live results use the first-party KX result model and shared durable `vscode-kdb.results.*` settings while their in-memory records exist. Each opaque record is bound to its notebook URI and cell URI; rerun replaces it, cell removal removes it, notebook close removes it, deactivation clears all records, and the 512-record cap evicts the oldest. Saved `.ipynb` output contains only the safe bounded portable snapshot; reopening cannot recover omitted data. Provider/fake and contract tests cover these boundaries, and the notebook-results harness performs a real direct-q Extension Host run plus a tracked-file reopened-preview capture. Automation of the top-right controller selector itself remains outstanding.

### M3.3 — mixed q action and notebook Results convergence (0.2.5)

This release keeps Python selected for mixed notebooks and adds an explicit q-language-cell **Run q Cell (KX)** gesture through the same direct query/session/result core as the native q controller. The focused-editor shortcut is q-only and disabled under the direct controller; normal Python Run remains Jupyter-owned. Public VS Code APIs still select one controller for the notebook, so the mixed action does not fake native KX execution ownership: after stale-state checks it commits finished output as an undoable notebook edit, which marks the document dirty and replaces that q cell's internal handle while preserving source, language, metadata, and siblings.

The current Unreleased renderer and panel consume shared labels, output formats, chart families, settings definitions, summaries, focus treatment, and theme tokens. Inline tables expose the established Output/Columns/Settings model, selection or full-visible copy/export, explicit live/saved state, and exact live-value panel handoff. All six chart types use compatible selectors, explicit Render, a persistent visible color-keyed legend, matching selector swatches, stable hidden series, readable token-based axes/grids, zoom/refine/reset, and PNG export. Notebook Settings presents stored font size `0` as **Auto** and supplies constrained scrolling plus Close/Escape/focus-return behavior. Saved output remains honestly bounded. Deterministic contracts cover shared definitions and live/saved/stale protocol paths. The notebook result visual gate retains 12 real-q Extension Host screenshots. Its acceptance scope is local Linux/Xvfb plus loopback q; remote/devcontainer acceptance was not run because the Docker daemon is unavailable. Broader product interaction coverage remains partial.

### M3.4 — discoverable mixed q routing and durable targets (0.2.6)

This release adds leading **Make q Cell (KX)** and **Run q Cell (KX)** actions, q-cell route status, and an explicit notebook-level saved-profile target while Python remains selected. Only stable profile ID/name metadata is written to the notebook. Renames resolve by ID; missing or removed profiles require replacement and never route to list order. The q-only controller remains native and uses the active profile, with no redundant mixed-mode controls.

Connection saves are verified before success is reported, all profiles are displayed, active selection is explicit, and removing the active profile does not silently choose another. Persisted table previews default to 20 rows, retain schema/count/truncation metadata, and do not imply that a saved notebook owns the transient full live result.

### M3.5 — persistence repair and Python-first controller lifecycle (0.2.8)

This release corrects 0.2.6's brittle same-turn readback assumption. A resolved application/global settings or Memento update is success; immediate logical state remains coherent through delayed VS Code propagation, while rejected writes retain safe rollback and divergent external settings are reconciled. Deterministic tests reproduce two-profile add, same-ID port edit, remove, active selection, and rejection behavior, and a scoped real Extension Host smoke uses the actual store with isolated state and cleanup. The same smoke verifies q-language and safe KX metadata through save, close, and reopen.

The mixed workflow is now the default. Python stays selected while **Make q Cell (KX)** supplies q language/highlighting, an explicit safe profile ID/name selects the target, and **Run q Cell (KX)** resolves the current profile/endpoint for every run. Missing targets never fall through. The legacy q-only controller is registered through public API only when `vscode-kdb.notebook.enableDirectController` is explicitly enabled; it is absent from kernel candidates by default. This does not remove VS Code's Jupyter kernel selector and is not visual UI automation.

### M5 — source-of-truth switch and backports
